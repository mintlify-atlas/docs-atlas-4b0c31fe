title: Agent variants

The multi-agent explanation system supports multiple **agent variants** that control how dependency cycles are analyzed and explained. Each variant uses different prompting strategies and analytical approaches to generate cycle explanations.

## Edge agent variants

Edge agents analyze individual dependency edges (A → B) within a cycle. The framework supports three edge variants, configurable via the `edge_variant` parameter in your mode configuration.

### E0: Factual dependency analysis

**Purpose:** Purely descriptive analysis without interpretation or refactoring suggestions.

**Prompt behavior:**
- Focuses on explaining what the dependency is and how it is used
- Does NOT propose refactorings
- Stays grounded in code and file paths
- Outputs: Edge, Where in A, What from B, How A uses it, Notes/uncertainty

**Source:** `explain_AS/agents/prompts/prompts_edge.py:30-43`

**Example configuration:**
```yaml
modes:
  - id: explain_factual
    params:
      orchestrator: multi_agent
      edge_variant: E0
      synthesizer_variant: S0
      auxiliary_agent: none
```

<Note>
E0 is the default variant and is recommended for experiments where you want to avoid biasing the refactoring agent with suggested solutions.
</Note>

### E1: Interpretive analysis

**Purpose:** Adds cautious intent inference based on naming and folder structure.

**Prompt behavior:**
- Includes all E0 capabilities
- May infer architectural intent from naming patterns
- Labels interpretations explicitly as such
- Outputs: Edge, Where in A, What from B, How A uses it, Likely intent (cautious), Notes/uncertainty

**Source:** `explain_AS/agents/prompts/prompts_edge.py:45-59`

**Example configuration:**
```yaml
modes:
  - id: explain_with_intent
    params:
      orchestrator: multi_agent
      edge_variant: E1
      synthesizer_variant: S0
      auxiliary_agent: boundary
```

<Tip>
Use E1 when folder structure and naming conventions carry meaningful architectural information in your codebase.
</Tip>

### E2: Decoupling suggestions

**Purpose:** Provides 1-2 plausible decoupling options per edge.

**Prompt behavior:**
- Includes all E0 capabilities
- Proposes concrete decoupling strategies
- Suggestions are clearly marked as non-authoritative
- Outputs: Edge, Where in A, What from B, How A uses it, Decoupling ideas (1-2, cautious), Notes/uncertainty

**Source:** `explain_AS/agents/prompts/prompts_edge.py:61-75`

**Example configuration:**
```yaml
modes:
  - id: explain_with_suggestions
    params:
      orchestrator: multi_agent
      edge_variant: E2
      synthesizer_variant: S0
      auxiliary_agent: none
```

<Warning>
E2 may introduce bias toward specific refactoring strategies. Use with caution in controlled experiments.
</Warning>

## Synthesizer agent variants

The synthesizer agent combines edge-level reports into a cohesive cycle-level explanation. Three variants are available via the `synthesizer_variant` parameter.

### S0: Neutral cycle explanation

**Purpose:** Produces cycle-level understanding WITHOUT proposing which edges to break.

**Prompt behavior:**
- Synthesizes edge reports into coherent narrative
- Explains how the cycle is formed and why it exists
- Does NOT recommend specific edges to break
- Outputs: Cycle summary, How the cycle is formed, Why this coupling exists, Impact/maintainability notes, Reminders/constraints

**Source:** `explain_AS/agents/prompts/prompts_synthesizer.py:31-44`

**Example configuration:**
```yaml
modes:
  - id: explain_neutral
    params:
      orchestrator: multi_agent
      edge_variant: E0
      synthesizer_variant: S0
      auxiliary_agent: none
```

<Note>
S0 is the default and recommended variant for unbiased refactoring experiments where the LLM refactoring agent should independently decide which edges to break.
</Note>

### S1: Concrete refactoring plan

**Purpose:** Proposes a minimal plan for breaking the cycle, including 1-2 candidate edges.

**Prompt behavior:**
- Includes all S0 capabilities
- Explicitly proposes which edge(s) to break
- Provides minimal refactoring strategy
- Emphasizes truly breaking cycles (not just moving them)
- Outputs: Cycle summary, How the cycle is formed, Candidate edge(s) to break, Justification, Minimal refactoring strategy, Risks/checks, Reminders/constraints

**Source:** `explain_AS/agents/prompts/prompts_synthesizer.py:45-66`

**Example configuration:**
```yaml
modes:
  - id: explain_with_plan
    params:
      orchestrator: multi_agent
      edge_variant: E0
      synthesizer_variant: S1
      auxiliary_agent: boundary
```

### S2: Trade-off analysis

**Purpose:** Compares multiple candidate edges and discusses refactoring trade-offs.

**Prompt behavior:**
- Provides ranked shortlist of 2-3 options
- Analyzes pros/cons for each candidate
- Recommends a choice with justification
- Outputs: Cycle summary, How the cycle is formed, Candidate edges to break (ranked 1-3), Trade-offs, Recommended choice and why, Suggested refactoring approach, Reminders/constraints

**Source:** `explain_AS/agents/prompts/prompts_synthesizer.py:67-88`

**Example configuration:**
```yaml
modes:
  - id: explain_with_comparison
    params:
      orchestrator: multi_agent
      edge_variant: E1
      synthesizer_variant: S2
      auxiliary_agent: graph
```

<Warning>
S1 and S2 introduce directional guidance that may reduce the diversity of refactoring approaches. Use these variants when you want more prescriptive explanations.
</Warning>

## Auxiliary agents

Auxiliary agents provide additional context to the synthesizer and reviewer agents. They do NOT appear in the final `prompt.txt`, but their outputs inform the synthesis process.

Configure via the `auxiliary_agent` parameter: `none`, `boundary`, `graph`, or `review`.

### none: No auxiliary context

**Purpose:** Default mode with no additional context beyond edge reports.

**Source:** `explain_AS/engine.py:79-87`

**Example:**
```yaml
params:
  orchestrator: multi_agent
  edge_variant: E0
  synthesizer_variant: S0
  auxiliary_agent: none
```

### boundary: Boundary heuristic agent

**Purpose:** Infers architectural boundaries from file paths and naming conventions.

**How it works:**
- Analyzes external connections (incoming/outgoing edges outside the cycle)
- Groups files by folder buckets (configurable depth)
- Provides samples of external dependencies per cycle node
- Output includes: Likely boundaries, Possible boundary violations, Notes/uncertainty

**Source:** `explain_AS/agents/boundary.py:235-260`

**Configuration knobs** (hardcoded in `boundary.py`):
- `BOUNDARY_MAX_SAMPLES_PER_DIR = 8`
- `BOUNDARY_MAX_FOLDER_BUCKETS_PER_DIR = 6`
- `BOUNDARY_FOLDER_BUCKET_DEPTH = 2`

**Example:**
```yaml
params:
  orchestrator: multi_agent
  edge_variant: E0
  synthesizer_variant: S0
  auxiliary_agent: boundary
```

<Accordion title="View boundary agent prompt structure">
The boundary agent receives:
- Cycle chain
- External connections per cycle file (incoming and outgoing)
- Folder-bucketed summaries with sample paths

Prompt preamble (from `boundary.py:22-30`):
```
You are the Boundary Heuristic Agent.
You infer likely architectural boundaries from file paths and naming only.

Rules:
- Be cautious: do not assume frameworks.
- No tables, no JSON.
- Keep it short and helpful.
- If you see truncation notes, assume some context may be missing.
```
</Accordion>

### graph: Structural context agent

**Purpose:** Summarizes how the cycle sits within its containing strongly connected component (SCC).

**How it works:**
- Receives the full SCC node and edge list
- Identifies hubs, bridges, and structural patterns
- Output includes: How the cycle sits in the SCC, Hubs/bridges, External connections, Risks when breaking edges, Notes/uncertainty

**Source:** `explain_AS/agents/graph.py:79-104`

**Example:**
```yaml
params:
  orchestrator: multi_agent
  edge_variant: E0
  synthesizer_variant: S0
  auxiliary_agent: graph
```

<Accordion title="View graph agent prompt structure">
Prompt preamble (from `graph.py:15-24`):
```
You are the Structural Context Agent.
You receive the cycle and SCC graph context as plain text (nodes and edges).
Your job is to summarize how the cycle sits within the SCC.

Rules:
- Stay factual based on provided SCC text.
- No tables, no JSON.
- Keep it short and focused.
- If you see truncation notes, assume some context may be missing.
```
</Accordion>

### review: Reviewer agent

**Purpose:** Rewrites the synthesizer output for clarity and internal consistency.

**How it works:**
- Receives synthesizer output, edge reports, and auxiliary context
- Prioritizes synthesizer output in token budget allocation
- Rewrites for clarity WITHOUT adding new facts
- Does NOT include meta-commentary or critique
- Replaces synthesizer output in the final `prompt.txt`

**Source:** `explain_AS/agents/review.py:131-160`

**Token budget allocation** (from `review.py:84-86`):
1. Allocate maximum possible tokens to synthesizer output
2. Remaining tokens shared evenly across edge reports + aux context

**Output format:**
- Cycle summary
- How the cycle is formed
- Why this coupling exists (cautious interpretation)
- Impact/maintainability notes
- Reminders/constraints

**Example:**
```yaml
params:
  orchestrator: multi_agent
  edge_variant: E0
  synthesizer_variant: S0
  auxiliary_agent: review
```

<Note>
The review agent is unique: it REPLACES the synthesizer output rather than providing auxiliary context. Use it when you want improved coherence in the final explanation.
</Note>

<Accordion title="View reviewer prompt rules">
From `review.py:19-28`:
```
You are the Reviewer Agent.
You are a finalizer: rewrite the synthesizer output to be clearer and internally consistent.

Hard rules:
- Do NOT add new facts.
- Do NOT include meta commentary, critiques, or headings like "Issues found" or "Suggested revisions".
- Output ONLY the final revised cycle explanation, in the requested output format.
- No tables, no JSON.
- If you see truncation notes, assume some context may be missing.
```
</Accordion>

## Combining variants for experimental modes

You can mix and match variants to create custom experimental configurations:

```yaml
modes:
  # Minimal factual explanation
  - id: minimal
    params:
      orchestrator: multi_agent
      edge_variant: E0
      synthesizer_variant: S0
      auxiliary_agent: none

  # Interpretive with boundary context
  - id: interpretive_boundary
    params:
      orchestrator: multi_agent
      edge_variant: E1
      synthesizer_variant: S0
      auxiliary_agent: boundary

  # Prescriptive with structural analysis
  - id: prescriptive_graph
    params:
      orchestrator: multi_agent
      edge_variant: E0
      synthesizer_variant: S1
      auxiliary_agent: graph

  # Polished trade-off analysis
  - id: polished_comparison
    params:
      orchestrator: multi_agent
      edge_variant: E1
      synthesizer_variant: S2
      auxiliary_agent: review
```

<Tip>
Start with E0+S0+none for baseline experiments, then incrementally add variants to measure their impact on refactoring outcomes.
</Tip>
