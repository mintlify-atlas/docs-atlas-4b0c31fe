title: Results structure

---

All experimental outputs are stored in a structured directory hierarchy under `results_root` (configured in `pipeline.yaml`). This structure enables systematic analysis, reproducibility, and post-hoc inspection of all refactoring attempts.

## Top-level structure

```
results/
└── {experiment_id}/
    ├── {project_name}/
    │   ├── {branch_name}/
    │   │   ├── baseline/
    │   │   ├── {mode_id}/
    │   │   │   ├── {cycle_id}/
    │   │   │   └── ...
    │   │   └── ...
    │   └── ...
    └── ...
```

### Path components

- **`{experiment_id}`**: Top-level experiment identifier from `pipeline.yaml`
- **`{project_name}`**: Repository name from `repos.txt`
- **`{branch_name}`**: Git branch (usually `main` or `master`)
- **`baseline`**: Baseline dependency analysis (SCC reports, metrics)
- **`{mode_id}`**: Experimental mode identifier (e.g., `explain_E0_S0_noaux`)
- **`{cycle_id}`**: Individual cycle identifier (e.g., `scc_3_cycle_17`)

## Baseline directory

Created by `scripts/run_baseline.sh`.

```
results/{experiment_id}/{project_name}/{branch}/baseline/
├── dependency_graph.json
├── scc_report.json
├── cycle_catalog.json
├── metrics.json
└── status.json
```

### Artifact descriptions

<Accordion title="dependency_graph.json">
**Purpose:** Module-level dependency graph extracted from the codebase.

**Format:** JSON with nodes and edges.

**Generated by:** `ATD_identification/analyze_cycles.sh` (Python) or `analyze_cycles_dotnet.sh` (C#)

**Contains:**
- Node list (module file paths)
- Edge list (source → target dependencies)
- Language metadata
</Accordion>

<Accordion title="scc_report.json">
**Purpose:** Strongly connected components (SCCs) identified in the dependency graph.

**Format:** JSON with SCC structure.

**Contains:**
- List of SCCs with IDs
- Nodes per SCC
- Edges within each SCC
- SCC size statistics

**Example structure:**
```json
{
  "sccs": [
    {
      "id": "scc_3",
      "nodes": [{"id": "src/module_a.py"}, {"id": "src/module_b.py"}],
      "edges": [{"source": "src/module_a.py", "target": "src/module_b.py"}]
    }
  ]
}
```
</Accordion>

<Accordion title="cycle_catalog.json">
**Purpose:** Catalog of all architectural dependency cycles extracted from SCCs.

**Format:** JSON with cycle metadata.

**Generated by:** `scripts/build_cycles_to_analyze.sh`

**Contains:**
- Cycle ID (format: `scc_{N}_cycle_{M}`)
- Cycle nodes (file paths)
- Cycle edges
- Cycle size

**Used by:** Cycle selection logic to populate `cycles_to_analyze.txt`
</Accordion>

<Accordion title="metrics.json">
**Purpose:** Baseline code-quality and architectural metrics.

**Generated by:** `code_quality_checker/quality_collect.sh`

**Contains:**
- Cyclomatic complexity
- Maintainability index
- Lines of code
- SCC count and sizes
- Other language-specific metrics
</Accordion>

<Accordion title="status.json">
**Purpose:** Pipeline execution status and metadata.

**Contains:**
- Phase completion status
- Timestamp
- Error messages (if any)
- Execution context
</Accordion>

## Mode directory

Created by `scripts/run_llm.sh` for each experimental mode.

```
results/{experiment_id}/{project_name}/{branch}/{mode_id}/
├── cycle_0/
├── cycle_1/
├── ...
└── status.json
```

Each cycle has its own subdirectory containing all artifacts for that specific refactoring attempt.

## Cycle directory structure

### Explanation phase artifacts

```
results/{experiment_id}/{project_name}/{branch}/{mode_id}/{cycle_id}/
├── prompt.txt
├── transcript.txt
├── usage.json
├── explain_status.json
```

<Accordion title="prompt.txt">
**Purpose:** Final prompt sent to the refactoring agent (OpenHands).

**Content (from `engine.py:204-207`):**
1. Minimal base prompt with cycle nodes
2. Final cycle-level explanation (synthesizer or reviewer output)

**Does NOT include:**
- Individual edge reports
- Auxiliary agent outputs

These are available in `transcript.txt` but not in the final prompt.

**Example:**
```
You are analyzing a dependency cycle in a Python codebase.

Cycle nodes:
- src/domain/user.py
- src/services/auth.py
- src/domain/session.py

[Synthesizer output explaining the cycle...]
```
</Accordion>

<Accordion title="transcript.txt">
**Purpose:** Complete transcript of all LLM interactions during explanation phase.

**Contains:**
- All agent prompts (edge, boundary, graph, synthesizer, review)
- All LLM responses
- Token usage per call
- Timestamps

**Format:** Chronological log of all LLM API calls.

**Use case:** Debugging, understanding agent reasoning, auditing LLM behavior.
</Accordion>

<Accordion title="usage.json">
**Purpose:** Token usage statistics for explanation phase.

**Contains:**
- Total input tokens
- Total output tokens
- Per-agent token counts
- Estimated cost (if applicable)

**Example:**
```json
{
  "total_input_tokens": 15234,
  "total_output_tokens": 3421,
  "agents": {
    "edge": {"input": 8000, "output": 1200},
    "synthesizer": {"input": 5234, "output": 1500}
  }
}
```
</Accordion>

<Accordion title="explain_status.json">
**Purpose:** Explanation phase execution status.

**Contains:**
- Success/failure status
- Error messages (if any)
- Timestamp
- Mode parameters used
</Accordion>

### Refactoring phase artifacts

```
results/{experiment_id}/{project_name}/{branch}/{mode_id}/{cycle_id}/
├── openhands_workspace/
├── openhands_logs/
├── trajectory.json
├── patch.diff
├── refactor_status.json
```

<Accordion title="openhands_workspace/">
**Purpose:** OpenHands execution workspace (temporary, usually cleaned up).

**Contents:** Cloned repository, temporary files, build artifacts.

**Note:** Often removed after execution to save disk space. The `patch.diff` preserves all code changes.
</Accordion>

<Accordion title="openhands_logs/">
**Purpose:** OpenHands agent execution logs.

**Contains:**
- Agent action logs
- Terminal output
- Debugging information
- Error traces

**Use case:** Diagnosing OpenHands failures, understanding refactoring steps.
</Accordion>

<Accordion title="trajectory.json">
**Purpose:** Structured log of all OpenHands actions and observations.

**Format:** JSON array of action-observation pairs.

**Contains:**
- Actions taken by the agent (edit, run, commit, etc.)
- Observations (file contents, command outputs, test results)
- Timestamps
- Agent reasoning (if available)

**Use case:** Replaying refactoring process, analyzing agent behavior.
</Accordion>

<Accordion title="patch.diff">
**Purpose:** Complete Git patch of all code changes made by OpenHands.

**Format:** Unified diff format.

**Generated by:** `git diff` after OpenHands commit.

**Contents:** All file modifications, additions, deletions.

**Use case:**
- Reviewing refactoring changes
- Applying changes to other branches
- Auditing code transformations
- Measuring change size and scope

**Example:**
```diff
diff --git a/src/domain/user.py b/src/domain/user.py
index 1234567..abcdefg 100644
--- a/src/domain/user.py
+++ b/src/domain/user.py
@@ -10,7 +10,7 @@ class User:
-    from src.services.auth import validate_session
+    # Removed circular dependency
```
</Accordion>

<Accordion title="refactor_status.json">
**Purpose:** Refactoring phase execution status.

**Contains:**
- Success/failure status
- OpenHands exit code
- Commit hash (if successful)
- Error messages
- Execution time
</Accordion>

### Post-refactoring metrics

```
results/{experiment_id}/{project_name}/{branch}/{mode_id}/{cycle_id}/
├── post_metrics.json
├── post_scc_report.json
├── test_results.json
```

Generated by `scripts/run_metrics.sh`.

<Accordion title="post_metrics.json">
**Purpose:** Code-quality metrics after refactoring.

**Format:** Same as baseline `metrics.json`.

**Use case:** Comparing before/after metrics to measure refactoring impact.

**Metrics include:**
- Cyclomatic complexity
- Maintainability index
- SCC count and sizes
- Lines of code changed
</Accordion>

<Accordion title="post_scc_report.json">
**Purpose:** SCC analysis after refactoring.

**Format:** Same as baseline `scc_report.json`.

**Use case:** Verifying that the cycle was actually broken.

**Success criteria:**
- Target cycle no longer appears in SCC report
- No new cycles introduced
- SCC count reduced or unchanged
</Accordion>

<Accordion title="test_results.json">
**Purpose:** Test suite execution results after refactoring.

**Contains:**
- Test pass/fail counts
- Test output
- Coverage changes (if available)
- Execution time

**Use case:** Ensuring refactoring did not break functionality.
</Accordion>

## Status tracking and resume

The pipeline uses `status.json` files to track completion and enable resume functionality.

### Status file locations

```
results/{experiment_id}/{project_name}/{branch}/baseline/status.json
results/{experiment_id}/{project_name}/{branch}/{mode_id}/status.json
results/{experiment_id}/{project_name}/{branch}/{mode_id}/{cycle_id}/explain_status.json
results/{experiment_id}/{project_name}/{branch}/{mode_id}/{cycle_id}/refactor_status.json
```

### Status values

- **`complete`**: Phase finished successfully
- **`failed`**: Phase encountered an error
- **`blocked`**: Phase was interrupted (LLM unavailable, crash, etc.)
- **`partial`**: Incomplete execution (discarded on resume)

### Resume behavior

From the [smoke testing documentation](/advanced/troubleshooting#smoke-testing):

<Note>
The pipeline verifies that:
- Incomplete phases are detected
- Partial results are discarded safely
- Completed work is not recomputed
- Interrupted experiments can be resumed correctly
</Note>

When you re-run `scripts/run_llm.sh` or `scripts/run_metrics.sh`:

1. **Completed units**: Skipped (status = `complete`)
2. **Blocked units**: Re-executed from scratch
3. **Partial units**: Cleaned and re-executed
4. **Failed units**: Re-executed (unless `--skip-failed` flag used)

## Inspecting results

### Viewing explanation quality

```bash
# Read final prompt sent to OpenHands
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/prompt.txt

# Read full transcript with all agent interactions
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/transcript.txt

# Check token usage
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/usage.json
```

### Reviewing refactoring changes

```bash
# View complete diff
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/patch.diff

# Check refactoring status
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/refactor_status.json

# Inspect OpenHands trajectory
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/trajectory.json | jq .
```

### Comparing metrics

```bash
# Baseline metrics
cat results/expA/myproject/main/baseline/metrics.json

# Post-refactoring metrics
cat results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/post_metrics.json

# Compare SCC counts
jq '.scc_count' results/expA/myproject/main/baseline/metrics.json
jq '.scc_count' results/expA/myproject/main/explain_E0_S0_noaux/scc_3_cycle_17/post_metrics.json
```

## Archiving and reproducibility

All experimental artifacts are preserved locally:

<Tip>
**For reproducibility:**

1. Archive the entire `results/` directory after experiments
2. Include `configs/pipeline.yaml` and `repos.txt`
3. Document the Docker image versions used
4. Preserve `cycles_to_analyze.txt` for exact cycle selection

This enables full post-hoc analysis and independent verification of results.
</Tip>

### Disk space management

Large experiments can generate significant data:

```bash
# Check results directory size
du -sh results/

# Remove OpenHands workspaces (keep diffs)
find results/ -type d -name "openhands_workspace" -exec rm -rf {} +

# Compress old experiments
tar -czf results_expA.tar.gz results/expA/
```

<Warning>
Do NOT delete `patch.diff` files - they contain the only record of code changes if workspaces are cleaned.
</Warning>

## Results analysis workflow

Typical analysis pipeline:

1. **Extract metrics** from all `post_metrics.json` files
2. **Identify successful refactorings** (cycle broken, tests passing)
3. **Measure code quality changes** (complexity, maintainability)
4. **Analyze failure modes** (OpenHands logs, error messages)
5. **Compare modes** (which variants produced better outcomes?)
6. **Inspect trajectories** (how many steps? what strategies?)
7. **Review patches** (are changes architecturally sound?)

Example Python script structure:

```python
import json
from pathlib import Path

results_root = Path("results/expA")

for cycle_dir in results_root.rglob("scc_*_cycle_*"):
    mode = cycle_dir.parent.name
    cycle = cycle_dir.name
    
    # Load artifacts
    with open(cycle_dir / "refactor_status.json") as f:
        status = json.load(f)
    
    with open(cycle_dir / "post_metrics.json") as f:
        metrics = json.load(f)
    
    # Analyze...
    if status["success"]:
        print(f"{mode}/{cycle}: Success - SCC count: {metrics['scc_count']}")
```

<Note>
The structured directory layout and consistent JSON formats make automated analysis straightforward.
</Note>
